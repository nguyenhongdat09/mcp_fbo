## 2) BA LỖI CẦN SỬA (BẮT BUỘC)

### Lỗi A — `get_kuzu_store` / MCP query không reopen khi DB đổi

`mcp_query_radar` gọi:

```python
store = get_kuzu_store(reference_file)
results = store.execute_cypher(cypher_query)
```

`get_kuzu_store` cache mãi `KuzuIndexStore(read_only=True)`.  
Khi watcher (cùng hoặc khác thread) đã ghi disk + invalidate, **hoặc** disk bị process khác cập nhật, query MCP vẫn dùng connection RO cũ → Cypher thấy snapshot cũ.

`xml_graph_query` có check mtime để reload `_graph_cache`, nhưng:

- Reload vẫn qua **cùng store/connection RO cũ** → `load_graph()` / `execute_cypher` vẫn có thể stale.
- `mcp_query_radar` **bỏ qua** luôn nhánh mtime đó.

**Yêu cầu:**

Trước mọi read MCP / engine:

1. Lấy `mtime` (và ideally size) của file/dir `kuzu`.
2. Nếu khác lần mở store trước → `close_cached_database` + xóa `_kuzu_stores` / `_store_cache` / `_graph_cache` cho project đó → mở lại `read_only=True`.
3. Áp dụng cho:
   - `get_kuzu_store`
   - `mcp_query_radar` / mọi tool đọc Kuzu
   - `xml_graph_query` (không chỉ đổi graph in-memory; phải reconnect store nếu mtime đổi)

Gợi ý API:

```python
def ensure_fresh_readonly_store(db_path: Path, graph_dir: Path) -> KuzuIndexStore:
    """Reopen RO store if kuzu mtime/size changed since last open."""
```

Log ngắn khi reopen: `[CodeGraph] Kuzu mtime changed → reopen read-only store`.

### Lỗi B — Nhiều process MCP giữ RO lock / cache riêng

Có nhiều `fastbusiness_mcp.exe` → watcher process A update disk; query process B không biết → stale.

**Yêu cầu thực dụng (không cần IPC phức tạp ngay):**

1. Khi start MCP / start watcher: log PID + db_path + “recommend single MCP instance per machine for same KuzuDB”.
2. Reader: **mtime-based reopen** (Lỗi A) đủ để process B thấy data mới **sau khi** disk đổi, miễn là không giữ snapshot mãi.
3. Writer: trước write vẫn `invalidate` + `close` trong process writer; retry lock (Lỗi C).
4. Nếu phát hiện không lấy được write lock sau retries: log ERROR rõ (PID/path), không giả success.
5. Rà `run_server.py` / spec / chỗ spawn MCP — tránh tự spawn thêm instance vô ích (chỉ sửa nếu chắc chắn).

Không được: bắt buộc user kill process như giải pháp duy nhất trong DoD.  
Được: document + log cảnh báo multi-instance.

### Lỗi C — Retry lock không chạy vì nuốt exception

Trong `incremental_update_file` / `delete_node_by_path`:

```python
except Exception as e:
    print(...)
    return None
```

Trong khi `run_incremental_write` chỉ retry khi **exception bubble**.

Evidence: log chỉ có `incremental_update_file error: Could not set lock` rồi `write_result None` — **không** có `Attempt 1/5: Lock conflict`.

**Yêu cầu:**

Cách 1 (ưu tiên): với lỗi lock/IO → **re-raise** từ `incremental_update_file` / `delete_node_by_path` để `run_incremental_write` retry.

Cách 2: `run_incremental_write` nếu `node is None` và log/err gần nhất chứa lock → coi như fail và retry (kém sạch hơn).

Không được: `return None` rồi vẫn `invalidate` và coi như xong im lặng.

Sau hết retries: `ERROR: Failed to write ... after N retries` (đã có) — giữ.
