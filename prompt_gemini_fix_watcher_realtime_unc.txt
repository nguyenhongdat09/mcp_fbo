## 3) PHÂN TÍCH NGUYÊN NHÂN (CẦN TỰ XÁC MINH — ĐÃ CÓ MANH MỐI)

Hãy đọc code rồi **chứng minh/bác bỏ** từng giả thuyết bằng log/test:

### G1) Watchdog Observer mặc định không tin cậy trên UNC

`start_watcher` dùng `watchdog.observers.Observer` (Windows: ReadDirectoryChangesW).  
Trên `\\server\share\...` event modify **thường không tới**.

→ Cần **PollingObserver** (hoặc hybrid: local=Observer, UNC/network=PollingObserver).

### G2) Nhiều process MCP cùng giữ lock file Kuzu

Nhiều `fastbusiness_mcp.exe` mở cùng `C:\KuzuDB\...\kuzu` → writer không set lock được.

→ Trong cùng 1 process: close RO trước write (đã có một phần).  
→ Cross-process: giảm số connection giữ lâu / document 1 MCP instance; nếu có thể, writer retry + log process lock; không được im lặng fail.

### G3) Thứ tự close/write/invalidate chưa đủ chặt

Hiện watcher gọi `incremental_update_file` rồi mới `invalidate_project_cache`.  
`incremental_update_file` dựa vào reopen RO→RW trong `KuzuIndexStore.__init__`.

Yêu cầu: **trước khi write**, chủ động:

1. Invalidate `_store_cache` / `_graph_cache` / `_kuzu_stores` / engine caches
2. `close_cached_database(db_path)` + GC nếu cần
3. Mở `read_only=False`
4. `update_single_node`
5. Invalidate lại caches đọc để query sau không dùng graph cũ trong RAM

### G4) Watcher chỉ start sau query MCP đầu tiên

`start_watcher_for_project` trong `mcp_tools.get_kuzu_store`.  
Nếu chưa từng query project → không watch.

→ Giữ hành vi lazy-start OK, nhưng khi đã start phải hoạt động; log rõ “watcher started for UNC path X with PollingObserver”.

### G5) In-memory graph cache stale

Dù DB đã ghi, `xml_graph_query` / MCP có thể trả `_graph_cache` cũ nếu không invalidate.

→ Sau incremental thành công bắt buộc clear cache đọc của project đó.

## 4) THIẾT KẾ CẦN IMPLEMENT

### 4.1 Chọn Observer theo path

Trong `xml_codegraph/service/watcher.py` (và chỗ `start_watcher`):

```text
Nếu controllers_root là UNC (\\\\server\share) hoặc network drive:
    dùng PollingObserver (interval hợp lý, ví dụ 1–2s, có thể config)
Else:
    dùng Observer mặc định (hoặc Polling nếu config ép)
```

- Debounce per-file giữ nguyên (tránh storm).
- Vẫn chỉ schedule các `get_graph_scan_roots` (Dir/Grid/Filter/…).
- Log: `Using PollingObserver interval=Xs for UNC path ...`

Có thể thêm config (tách khỏi `fbograph` storage nếu cần), ví dụ:

```yaml
watcher:
  polling_forced: 0          # 1 = luôn poll
  polling_interval_sec: 1.5  # dùng khi UNC hoặc forced
```

Nếu thêm config: **đừng nhét vào** block `fbograph.kuzu_db_base`. Block riêng `watcher:` hoặc `extract_options` nếu team đã có convention — ưu tiên block `watcher:`.

### 4.2 API write an toàn (single-file)

Tạo/chuẩn hóa helper dùng chung cho watcher + incremental, kiểu:

```python
def run_incremental_write(file_path, controllers_root, graph_dir) -> Optional[GraphNode]:
    # 1) acquire per-db lock
    # 2) invalidate + close_cached_database
    # 3) incremental_update_file / delete_node_by_path
    # 4) invalidate caches again
    # 5) return node or raise/log failure clearly
```

`GraphUpdateHandler.on_any_event` phải gọi helper này — không full rebuild.

### 4.3 Giữ nguyên semantics incremental

Đọc và giữ đúng:

- `incremental_update_file` — re-parse 1 file, rebuild outbound edges của node đó, backup/restore inbound nếu đang làm vậy
- `delete_node_by_path` — delete/rename
- Pairing `.xml` / `.f` hiện có trong watcher

**Không** đổi sang rebuild toàn Controllers.

### 4.4 Connection / lock (bổ sung trên nền v2)

Đã có: cache `_db_instances` kèm `read_only`, reopen khi mismatch.  

Bổ sung bắt buộc:

- Trước write: close + invalidate **proactive** (không chỉ dựa mismatch lúc `__init__`)
- Per-db `RLock` bao trùm cả close→open→update (query thread không đọc giữa chừng)
- Nếu open write fail vì lock: **retry ngắn có backoff** + log rõ; cuối cùng log ERROR (không giả success)
- Sau write success: reader query sau mở lại RO từ data mới

### 4.5 Multi-process (thực dụng)

Không cần IPC phức tạp ngay, nhưng phải:

1. Log khi không lấy được lock (kèm path DB).
2. Tránh mở thêm writer từ process lạ nếu có thể phát hiện.
3. Trong docstring/README ngắn hoặc log startup: khuyến nghị **1 instance MCP** / project.
4. Nếu có chỗ spawn nhiều `fastbusiness_mcp` vô tình — tìm và giảm (không phá MCP Cursor config của user nếu không chắc).
